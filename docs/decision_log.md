# ReplyFlow 决策日志 v1.0

> 本文件记录阶段 1 已冻结的关键产品与技术决策。后续如果要推翻某条决策，必须新增一条决策记录说明原因，而不是直接覆盖。

## ADR-001：产品形态选择嵌入顶部聚合站内信

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | ReplyFlow 作为 AI 回复能力嵌入顶部聚合站内信，不做独立聊天产品 |
| 原因 | 店管实际处理对象是聚合后的买家会话；AI 回复应减少切换成本，顺着现有邮件处理路径进入 |
| 影响 | 页面必须包含原始收件箱、顶部聚合站内信、回复区、订单/依据/Trace 侧栏；完整 AI 能力只出现在顶部聚合站内信 |
| 放弃 | 独立客服 Agent 首页、独立聊天窗口、全新客服系统 |

## ADR-002：唯一业务角色为店管

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | 第一版只保留店管一个业务角色 |
| 原因 | 作品目标是证明 Agent 嵌入回复流程和高风险人机协同，不是证明组织权限或多人流程 |
| 影响 | 不做登录、角色切换、权限矩阵、审批队列；三级风险由店管核对，不引入其他人 |
| 放弃 | 客服主管、管理员、多角色协作 |

## ADR-003：取消政策邮件与政策治理

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | 只做客服回复，不做亚马逊官方政策邮件识别、政策文件夹和政策治理 |
| 原因 | 政策治理会把项目方向从“客服回复 Agent”拉到“规则知识管理系统”，工作量变大且面试主线分散 |
| 影响 | 原始收件箱可展示非买家消息，但不会抽取政策、建政策目录或管理政策版本 |
| 保留 | 项目内部虚构回复依据，只读检索，用于生成回复 |

## ADR-004：采用 Dify + 自建控制层

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | Dify 负责意图识别、实体抽取和英文草稿等概率型 AI 能力；Python 自建控制层负责状态、工具、风险、确认、幂等、审计和本地模拟发送 |
| 业务原因 | 高风险售后回复的关键不是“能不能生成一句英文”，而是能否把自动化边界、证据链、确认动作和写入限制做成可解释的业务闭环 |
| 为什么不全用 Dify | 页面状态、重复发送、核对清单、风险网关和本地 outbox 需要可测试的确定性控制；完全藏在可视化编排里，不利于证明业务边界 |
| 为什么不全自研 | 模型编排和 Prompt 调试变化快，完全自研会消耗过多时间，不符合个人作品 MVP 的投入产出 |
| 影响 | 后续必须区分 Demo Mode 与 Interactive Mode；Dify 不能覆盖本地风险判定，不能执行写操作 |

## ADR-005：全部使用虚构数据

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | 所有邮件、订单、物流、店铺、客户、回复依据和评测数据全部虚构 |
| 原因 | 项目服务于作品集，不依赖公司真实系统和数据；避免隐私、商业信息和合规风险 |
| 影响 | 种子数据统一使用 `example.com` 邮箱和虚构订单；截图、录屏、HTML/PDF 不出现真实公司业务数据 |
| 放弃 | 连接真实 Amazon、邮箱、OMS、支付、物流或公司数据库 |

## ADR-006：所有发送都是本地模拟写入

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | `send_simulated_reply` 只写入本地 SQLite outbox，不连接真实外部发送接口 |
| 原因 | 作品目标是展示流程控制和风险边界，不需要也不应该产生真实业务动作 |
| 影响 | 页面必须持续提示“模拟发送”；Trace 和 outbox 可以证明状态变化 |
| 放弃 | 真实邮件发送、真实退款、修改订单、修改地址、取消订单 |

## ADR-007：演示必须动态接入，不只做静态页面

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | 设置折叠的“演示控制台（模拟邮件接入）”，支持输入一行邮件并真实进入收件箱和聚合站内信 |
| 原因 | 面试中最有说服力的是从新邮件进入开始展示状态变化；静态 HTML 只能解释方案，不能证明 Agent 闭环 |
| 影响 | 后续 UI 必须支持计数变化、新会话置顶、状态刷新、工具 Trace、草稿写入和本地 outbox |
| 放弃 | 只展示静态截图、只展示固定已处理案例 |

## ADR-008：第一版不引入复杂工程框架

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | 第一版使用 Python 3.11、Streamlit、SQLite、Pydantic、MCP、Dify、pytest 和 JSONL；不引入 FastAPI、LangGraph、Docker、前端框架或 Multi-Agent |
| 原因 | 用户技术背景较弱，项目需要能通过 AI 编程逐步完成；复杂框架会增加调试和展示成本 |
| 影响 | 核心逻辑仍要模块化，不能全部写在 Streamlit 页面里；每阶段补测试 |
| 放弃 | 生产级微服务架构和复杂编排架构 |

## ADR-009：阶段式推进，每阶段必须提交并推送

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | 每次只完成行动指南中的一个阶段，阶段完成后更新状态、运行自查、提交 Git 并推送 GitHub |
| 原因 | 用户可能换电脑继续开发；分阶段提交可以降低丢失和跑偏风险 |
| 影响 | 未提交或未推送的修改不能视为完成；每个阶段报告修改文件、命令、测试、人工验收和下一步 |
| 放弃 | 一次性生成完整项目、长时间不提交的大改 |

## ADR-010：面试叙事以业务控制为主，技术名词为辅

| 项 | 内容 |
|---|---|
| 状态 | 已确认 |
| 日期 | 2026-08-20 |
| 决策 | 面试展示顺序为动态邮件接入、三级处理、工具证据、风险控制、评测，再解释 Skill、MCP、Dify |
| 原因 | 面试官首先关心为什么这个 Agent 对业务有意义，以及自动化边界是否清楚；技术概念要服务于业务结果 |
| 影响 | README、作品集和演示脚本都应避免堆技术名词；先让人看到流程和控制，再讲实现 |
| 放弃 | 把项目包装成“又一个智能客服 SaaS” |

## 变更规则

新增决策必须追加 `ADR-0xx`，包含状态、日期、决策、原因、影响和放弃方案。不要直接删除历史决策；若废弃，标记为“已废弃”并说明替代决策。
