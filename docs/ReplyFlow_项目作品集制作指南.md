# ReplyFlow 项目作品集制作指南

> 用途：指导将“一期亚马逊客服邮件工作台”和个人独立完成的 ReplyFlow Agent 整理成可投递、可面试、可追问的项目作品集。
>
> 适用对象：产品经理岗位，重点方向为供应链/电商 B 端产品、AI Agent、智能提效和人机协同。

## 1. 作品集的核心目标

这份作品集不是为了证明“我调用过一个大模型”，而是要让招聘方在 5 分钟内确认四件事：

1. 你理解真实的电商客服业务流程，而不是从一个空白聊天框开始想象产品。
2. 你能从原有 B 端系统中识别适合 AI 提效的环节，并把 Agent 嵌入原流程。
3. 你知道哪些事情可以自动化，哪些事情必须保留人工确认和风险拦截。
4. 你能把方案落成可演示原型，并用代码、评测和失败记录验证它，而不是只画概念图。

作品集的主线应当是：

```text
一期客服邮件工作台
  -> 观察客服回复中的重复劳动与风险边界
  -> 个人独立设计 ReplyFlow Agent
  -> 在原页面骨架上增量接入
  -> 按 L1/L2/L3 实现人机协同
  -> 用动态演示、评测和限制证明方案是否成立
```

## 2. 必须先讲清楚的项目关系

### 2.1 公司实习项目与个人项目必须分开标注

建议在封面或第二页明确分成两段：

| 部分 | 定义 | 可以证明什么 |
|---|---|---|
| 一期亚马逊客服邮件工作台 | 实习期间参与/负责的业务项目，以实际承担内容为准 | 真实业务理解、页面结构、客服邮件处理流程、订单上下文 |
| ReplyFlow Agent | 基于上述业务观察，实习后独立完成的个人研究型原型 | AI 产品设计、Agent 编排、人机协同、风险控制、原型落地能力 |

不要把个人 Agent 写成公司已经上线的功能。推荐表述：

> 我在实习期间参与了亚马逊客服邮件工作台的一期建设，理解了邮件接入、聚合、订单关联和回复处理流程。之后我基于这个业务场景独立完成 ReplyFlow，用于验证 AI 回复在原有工作台中的接入方式、自动化边界和高风险人机协同方案。

### 2.2 数据和系统边界必须主动声明

在 PDF、案例页和视频开头都要注明：

- 邮件、订单、物流、买家、店铺和回复均为虚构或本地模拟；
- 不连接真实 Amazon、公司邮箱、支付、退款或订单接口；
- 所有发送动作只写入本地模拟 outbox；
- Coze 负责意图识别、实体抽取和草稿生成；
- 本地控制层负责事实、风险、状态、确认、幂等和审计。

这样可以避免面试官误以为你泄露了公司数据，也避免把个人实验夸大为生产系统。

## 3. 最终交付物与格式

### 3.1 投递附件

主附件使用 PDF，不使用 HTML 作为唯一附件。

推荐文件名：

```text
姓名_产品经理_作品集.pdf
```

PDF 建议控制在 8-12 页、5-10 MB 以内。每页只表达一个判断，不要把完整 PRD 直接塞进作品集。

### 3.2 在线补充材料

| 材料 | 建议形式 | 作用 |
|---|---|---|
| 案例说明 | HTML/PDF | 讲清楚背景、方案、取舍和结果 |
| 动态 Agent 演示 | 2-3 分钟视频 | 证明邮件进入、聚合、分析、回复的动态过程 |
| 源码与文档 | GitHub | 应对技术追问，展示实现过程和测试 |
| 可运行页面 | 本地 `stage_b_server.py` | 面试现场展示，不作为普通附件直接打开 |
| 原始一期原型 | 未标注版/标注版 HTML | 作为业务基线和改造依据，不作为最终成品 |

PDF 最后一页放置 GitHub、在线案例页和视频链接。不要把 Coze PAT、`.env`、真实邮箱或本地密钥放进任何材料。

## 4. PDF 页面结构

### 第 1 页：封面与一句话定位

标题建议：

> 从客服邮件工作台到 ReplyFlow：高风险售后回复的人机协同验证

副标题：

> 基于一期电商客服邮件工作台的个人 AI Agent 研究型原型

封面必须出现：

- 你的姓名和目标岗位；
- 项目类型：实习项目延伸 / 个人独立项目；
- 一张原页面叠加 Agent 的清晰截图；
- 数据边界说明：虚构数据、本地模拟、不代表公司上线。

不要在封面放大段技术名词、完整架构图或“全自动客服”之类容易引起误解的宣传语。

### 第 2 页：项目关系、职责和背景

这一页要回答“这是什么项目、你做了什么”。

建议使用左右结构：

- 左侧：一期客服邮件工作台截图和业务流程；
- 右侧：你的实习职责、个人延伸边界和 Agent 项目目标。

必须区分：

- 哪些页面和业务理解来自一期项目；
- 哪些 Agent 设计、技术实现、评测和文档是你独立完成的；
- 哪些内容只是个人假设，未在公司落地。

职责描述必须以事实为准。没有亲自负责的内容使用“参与、协助、理解、基于此延伸”，不要统一写成“主导”。

### 第 3 页：原有流程与问题定义

不要直接说“客服工作重复，所以要做 AI”。要展示问题是如何从流程中发现的。

建议画出：

```text
邮件进入
  -> 店管打开单封邮件
  -> 判断订单和物流信息
  -> 查找回复依据
  -> 撰写英文回复
  -> 判断是否存在退款/拒付/承诺风险
  -> 发送或继续人工处理
```

然后指出三个具体问题：

1. 低风险物流咨询重复度高，但人工仍需重复查询和撰写；
2. 普通退换货咨询需要上下文和措辞判断，完全自动发送风险较高；
3. 退款、拒付、投诉、法律威胁或事实冲突不能交给模型直接决定。

问题定义建议写成：

> 如何在不改变店管现有邮件处理习惯的前提下，把适合自动化的回复交给 Agent，同时让高风险回复在发送前经过可解释、可阻断的人工核对？

### 第 4 页：为什么 Agent 必须嵌入原页面

这一页是产品判断的重点。

说明你没有做独立聊天机器人，原因包括：

- 店管的工作对象已经是顶部聚合站内信；
- 邮件、订单、物流和回复框已经存在；
- 另起页面会造成上下文切换；
- Agent 生成的结果最终仍要回到原回复框或发件流程；
- 在原页面上增量接入，才能验证真实的操作成本是否下降。

页面最好放“原页面”和“接入 Agent 后页面”的对照图，并用 3-5 个编号标出新增内容：

1. 顶部外部全局智能客服开关；
2. L1/L2/L3 风险与 AI 标识；
3. L2 草稿进入原回复框；
4. L3 高风险提示与核对清单；
5. 右下角模拟邮件台。

### 第 5 页：产品方案与处理分级

用一张表讲清楚 L1、L2、L3，不要只写“低、中、高风险”。

| 处理级别 | 典型场景 | Agent 行为 | 人工边界 |
|---|---|---|---|
| L1 自动回复 | 订单和物流事实完整的低风险查询 | 生成草稿，通过本地风险网关后写入本地模拟 outbox | 不逐封确认，但保留 Trace |
| L2 生成草稿 | 退货、换货、商品咨询、信息不足 | 草稿填入原回复框 | 店管编辑/确认后才能模拟发送 |
| L3 高风险核对 | 退款、拒付、投诉、法律威胁、事实冲突、工具失败 | 生成参考草稿并显示风险原因 | 核对清单未完成时发送被阻断 |

同时说明：

- R0-R3 是风险等级；
- L1-L3 是页面处理级别；
- 模型建议不能降低本地风险网关的结果；
- 草稿生成后还要再次扫描，防止模型自行加入退款、金额、责任或确定时限承诺。

### 第 6 页：动态流程与页面演示

这一页不要放静态功能清单，应展示一封邮件如何发生变化：

```text
模拟邮件台输入
  -> 写入原始收件箱
  -> 聚合为顶部站内信
  -> Coze Analyze
  -> 查询订单/物流/回复依据
  -> 本地风险分级
  -> Coze Draft
  -> L1 自动回复 / L2 草稿 / L3 高风险核对
```

至少放四张连续截图：

1. 智能客服关闭，页面保持一期客服工作台状态；
2. 模拟邮件浮窗输入正文并选择订单；
3. 邮件进入收件箱和顶部聚合站内信；
4. Agent 完成 L1/L2/L3 处理并更新详情区域。

截图下方标注每一步的输入、系统动作、页面变化和状态，不要只标注“AI 处理成功”。

### 第 7 页：技术架构与 Agent 组成

架构图只放面试需要理解的边界：

```text
HTML/CSS/JavaScript 页面
          |
本地 Python HTTP 服务与状态协调
          |
SQLite / 状态机 / 风险网关 / 审计 / outbox
          |
8 个 MCP Tools + 3 个 Skills
          |
Coze Analyze / Draft Workflow
```

需要讲清楚：

- Coze 擅长概率型能力：意图识别、实体抽取和自然语言草稿；
- 本地代码擅长确定性能力：事实查询、风险判断、状态推进、确认、幂等和审计；
- MCP Tools 是 Agent 可调用的受控能力，不等于允许模型任意写数据库；
- Skills 是可版本化的任务规范，分别负责邮件分流、回复草稿和风险路由；
- 写入类能力必须有 `confirmed`、`operation_id`，L3 还必须有完整核对清单。

不要在 PDF 中堆砌所有函数名。完整 Tool、Skill 和状态列表放 GitHub 文档，PDF 只解释职责边界。

### 第 8 页：方案取舍

至少回答三个选择题：

| 选择 | 采用方案 | 业务理由 |
|---|---|---|
| 产品形态 | 嵌入原有顶部聚合站内信 | 减少上下文切换，贴近店管工作路径 |
| 模型编排 | Coze + 本地控制层 | 保留快速编排效率，同时掌控风险与写入边界 |
| 演示方式 | HTML 页面 + 本地 Python 服务 | 页面接近真实产品，后端状态可动态变化和测试 |
| 数据方式 | 虚构数据 + 本地模拟 outbox | 可独立演示，避免隐私和真实业务副作用 |

也要写清楚放弃的方案：

- 完全使用 Coze：页面状态、幂等和高风险拦截难以作为独立业务边界验证；
- 完全自研模型编排：对个人 MVP 来说投入过大，降低验证效率；
- 独立聊天页面：脱离原客服流程，无法证明嵌入式提效；
- 真实 Amazon 接口：超出个人作品范围，也会带来隐私和副作用风险。

### 第 9 页：评测、失败和限制

这一页决定作品集是否可信。必须同时展示成功结果和失败结果。

建议展示：

- 案例数量和高风险案例数量；
- 动态邮件接入率；
- 未授权承诺违规数；
- 无依据订单事实违规数；
- 高风险召回率；
- Coze 调用失败、Schema 解析失败和重试结果；
- 最终 Go / No-Go 判断。

当前项目应诚实保留：

> Demo 高风险召回率为 61.5%，未达到安全上线门槛，因此结论为 No-Go。2026-09-03 Interactive 复测时 Coze 额度可用，30 条案例完成评测，但高风险召回为 61.5%、意图准确率为 64.3%，并出现 1 条未授权承诺和 4 条结构校验失败，仍不宣称生产可用。

这不是项目失败，而是你具备评测意识的证据。要继续解释：

- 保护性指标已经通过，说明风险承诺和无依据事实控制有效；
- 召回率不足说明路由覆盖和语义泛化仍需提升；
- 下一步应补充真实分布样本、边界案例、模型输出约束和人工复核数据。

不要把一次成功的页面演示写成“准确率 100%”或“可以上线”。

### 第 10 页：个人贡献与后续计划

用“我完成了什么”收尾，而不是再放一张技术图。

可按以下维度列出：

- 产品：场景收敛、嵌入式定位、L1/L2/L3 规则和交互设计；
- Agent：Coze Workflow、Analyze/Draft Schema、Skills 和 MCP Tools；
- 工程：本地 HTTP 服务、SQLite、状态机、风险网关、幂等和审计；
- 验证：动态演示、端到端测试、失败重试、评测报告和 ROI 敏感性分析；
- 交付：PRD、原型、案例说明、视频分镜和 GitHub 仓库。

后续计划只写与当前项目直接相关的三点：

1. 扩充覆盖多语言、复杂多诉求和身份冲突的评测集；
2. 优化 Coze 的结构化输出约束和失败重试策略；
3. 在有真实数据授权的前提下，再评估邮箱接入、权限和生产化部署。

## 5. 面试中必须讲清楚的六个判断

### 判断一：为什么做这个 Agent

推荐回答：

> 我不是为了证明大模型能写英文，而是想验证它在已有客服回复流程中能承担多少工作。物流查询适合自动处理，普通退换货适合生成草稿，退款、拒付和事实冲突必须保留人工核对。因此项目重点是自动化边界和人机协同，而不是“全自动客服”。

### 判断二：为什么不在公司直接推动落地

推荐回答：

> 这是我基于实习场景独立完成的个人原型，不代表公司已经具备接入条件。真实落地还需要数据授权、系统接口、权限、模型稳定性和 ROI 验证。我先用虚构数据验证流程和边界，避免把一个未经评测的想法直接包装成上线方案。

### 判断三：为什么不是一个普通客服机器人

推荐回答：

> 普通客服机器人通常关注回答内容，而 ReplyFlow 关注邮件进入现有工作台后的完整状态变化：邮件接入、订单事实、回复依据、风险判断、草稿写入、人工确认、模拟发送和审计。它的核心是嵌入已有 B 端流程，并控制 Agent 的动作边界。

### 判断四：为什么不完全用 Coze

推荐回答：

> Coze 适合快速编排模型分析和草稿生成，但页面状态、风险门槛、重复发送、核对清单和审计需要可测试的确定性控制。把这些全部藏在编排平台里，业务边界不容易验证，也不利于回放和追责。

### 判断五：为什么不完全自研

推荐回答：

> 个人作品的目标是验证产品方案，不是重新建设模型平台。完全自研会把大量时间消耗在模型调用、Prompt 调试和输出解析上。用 Coze 承担变化快的模型编排，用本地代码承担稳定的业务控制，更符合 MVP 的投入产出。

### 判断六：评测结果不好，为什么还放进作品集

推荐回答：

> 因为我把评测当作上线前的决策门槛，而不是只展示成功截图。当前高风险召回率还没有达到安全要求，所以我明确给出 No-Go，并说明问题集中在哪里、下一步如何补数据和优化规则。这比宣称 Agent 已经完全可用更能证明我理解 AI 产品的风险。

## 6. 动态演示的标准流程

面试现场打开阶段 B 页面，按照下面顺序演示：

1. 页面初始状态：一期客服工作台形态，智能客服全局开关关闭；
2. 打开右下角模拟邮件台，选择一个虚构订单并输入邮件；
3. 提交后展示原始收件箱和顶部聚合站内信变化；
4. 打开顶部全局智能客服，确认处理待处理邮件；
5. 展示 L1 自动回复和本地模拟 outbox；
6. 展示 L2 草稿进入原回复框，编辑后再模拟发送；
7. 展示 L3 草稿、高风险提示和未完成清单时的发送阻断；
8. 展示失败重试、Tool Trace、风险决策和审计记录；
9. 最后打开 PDF 或案例页，说明评测结果和限制。

现场演示的目标不是点击最多的功能，而是让面试官看懂这一条闭环：

```text
收到邮件 -> 聚合 -> 获取事实 -> 分级 -> 生成/发送 -> 人工边界 -> 留痕
```

## 7. 截图与视觉规范

- 截图优先展示原邮件工作台与 Agent 增量区域，不要单独截一张聊天框；
- 同一组截图保持浏览器尺寸、缩放比例和数据状态一致；
- 页面截图中持续保留“虚构数据/模拟发送”提示；
- L1 使用绿色、L2 使用中性色或黄色、L3 使用红色，但不要让颜色替代文字说明；
- 风险提示、全局开关、订单事实和回复框要在同一张关键截图中尽量形成上下文；
- 标注版原型的红点只用于解释变更，不放在 PDF 的主视觉位置；
- 不展示终端中的 `.env`、PAT、请求头、真实邮箱或个人路径。

## 8. GitHub 与链接检查

投递前确认：

- README 第一屏能看到项目定位、启动方式和数据边界；
- 唯一可运行入口是 `stage_b_server.py` + `prototype/stage_b/index.html`；
- 不再出现旧的 Streamlit 工作台或 `8506` 运行指引；
- PRD、技术图谱、评测报告和案例页均能从 README 找到；
- `.env`、PAT、SQLite 运行数据和本地日志没有被提交；
- 每次阶段性修改均已提交并推送到 GitHub；
- 访问链接不会暴露真实业务数据或密钥。

## 9. 投递前最终自查清单

### 内容

- [ ] 能在 30 秒内说清楚项目是什么、解决什么问题、你做了什么。
- [ ] 明确区分一期实习项目与个人 ReplyFlow 延伸。
- [ ] 解释了为什么 Agent 要嵌入原页面。
- [ ] 解释了 L1/L2/L3 与 R0/R1/R2 的区别。
- [ ] 解释了 Coze、本地控制层、MCP Tools 和 Skills 的分工。
- [ ] 展示了动态邮件接入，而不是只展示静态结果。
- [ ] 展示了高风险阻断、失败重试和审计留痕。
- [ ] 展示了评测结果和 No-Go 限制，没有只展示成功案例。

### 格式

- [ ] PDF 是简历附件的主文件。
- [ ] HTML 是在线案例页，不依赖面试官在本地启动服务才能看懂。
- [ ] 视频可以在没有 Coze 额度时作为演示兜底。
- [ ] GitHub 链接、视频链接和在线案例页链接全部可访问。
- [ ] 文件名、页面标题和项目名称统一为 ReplyFlow。

### 表述

- [ ] 没有把个人原型写成公司已上线功能。
- [ ] 没有声称真实 Amazon、邮箱、退款或订单写入。
- [ ] 没有声称“完全自动化”“100% 准确”或“可以直接生产”。
- [ ] 没有把模型输出当成最终风险判断。
- [ ] 没有隐藏失败案例、额度限制或评测 No-Go。

## 10. 推荐的最终目录

```text
投递包/
├─ 姓名_产品经理_作品集.pdf       # 主附件

├─ prototype/stage_b/              # Agent 主演示页
├─ stage_b_server.py               # 唯一运行服务
├─ docs/ReplyFlow_项目作品集制作指南.md
├─ docs/replyflow_case_study.html
├─ docs/replyflow_case_study.pdf
├─ docs/requirements/              # PRD 与行动指南
├─ docs/技术图谱.md
├─ docs/interview_script.md
```

最终作品集的判断标准不是“功能越多越好”，而是面试官能否沿着你的材料回答：业务问题是什么、Agent 为什么放在这里、它做了哪些决定、哪些决定不能交给它、你如何证明方案还不够成熟，以及下一步如何推进。
